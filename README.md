# Saath Brain

The AI brain of Saath: one Central Assistant coordinating specialist agents
to help people with everyday life.

## Hackathon submission (judges start here)

**What existed before vs during the event:** nothing in this repo
predates the event except standard open-source dependencies (below).
Every Saath feature -- agent hierarchy, memory, approvals, voice UI,
video studio, integrations -- was built for this hackathon.

**Run it (no outside accounts needed):**

```powershell
git clone <this-repo> Saath
cd Saath
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
# add your Meta Model API key: META_API_KEY=...  (never commit .env)
.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8091
```

Open http://127.0.0.1:8091/web/, register an account, and use the app.
Without a key, Saath runs in honest keyless mode: the offline stub
answers (marked `[stub]`) while tasks, audit, approvals, and demo
bookings keep working for real. `python -m unittest` (278 tests) and,
in `frontend/`, `npm run test:voice` (53 voice checks) verify the
checkout. The committed `web/` build matches `frontend/` sources --
rebuild with `npm run build` after changing them.

**Meta models used (all via Meta Model API, `https://api.meta.ai/v1`):**

| Model | Where it runs | What it does in Saath |
|---|---|---|
| `muse-spark-1.3` (`/responses`) | Meta Model API | Chat understanding, router planning, delegation plans, lesson storyboards, photo understanding |
| `muse-image-1.0` (`/images/generations`) | Meta Model API | Per-scene keyframe illustrations for video lessons |

No Contributor-tier IDs (refused at startup), no fine-tuning, no
training on user data. API key lives only in backend `.env`.

**Non-Meta components (labeled):** React/Vite/Tailwind UI;

**Recorded evidence:** `docs/submission/shots/` (dashboard dark/light/

## Folder map

- `model_client.py` - model layer: offline stub, or live Muse when META_API_KEY is set

- `manager.py` - the Daily Life manager: runs specialists, verifies results, reports up
- `memory.py` - memory rules: five layers, permission matrix, consent gates
- `tools.py` - tool framework: harmless tools run at once, consequential ones pause for approval
- `worker.py` - background worker: watches deadlines, records notifications, honours quiet hours
- `reminders.py` - the Reminder Agent: dated nudges with a required deadline
- `organiser.py` - the Daily Organiser Agent: today's briefing from real data
- `util.py` - tiny shared helpers
- `tests/` - checks that prove each milestone works
- `.env` - your local secrets (never shared, never committed)
- `.env.example` - template explaining each setting
- `requirements.txt` - Python packages this project needs

## Hands-free voice ("Hi Saath")

Tap **Voice** in the top bar (once per visit — browsers require a tap
before the mic may run), then say **Hi Saath** from any screen. Saath
answers "Yes?", opens Talk, and holds a voice conversation: it listens,
sends what you say, reads the reply aloud, and listens again. Say
**thank you** (or tap Stop) to end the conversation; the mic keeps
watching for Hi Saath until you tap Voice off. The mic pauses when the
tab is hidden, ignores Saath's own spoken replies, and everything runs
in the browser via built-in speech services — no audio is uploaded by
Saath. Works best in Chrome or Edge.

## Talk to the specialists through chat (server running, logged in as above)

```powershell
$h = @{Authorization = "Bearer $($login.token)"}
Invoke-RestMethod -Uri http://127.0.0.1:8000/chat -Method Post -Headers $h -Body (@{message='remind me to call mother tomorrow at 09:00 and give me my briefing'} | ConvertTo-Json) -ContentType 'application/json'
```

The Central Assistant splits the request and hands it to the Daily Life
manager, which runs one Reminder Agent task and one Daily Organiser task
as real linked child tasks, verifies their results against the stored
rows, and reports back; Central verifies the report and combines
everything into one reply. With a live key, the model plans the split
(understanding dates like "the day after tomorrow"); without one, or if
planning fails, deterministic rules backstop it. Either way a reminder
needs an explicit time (`tomorrow at 9am`, `today at 15:30`, `in 2
hours`, or an ISO date, all UTC), and the briefing answers to words like
"briefing", "my day", or "what's due". Anything else is answered
directly, and anything unclear is reported rather than guessed.

## Try gated tools (server running, logged in as above)

```powershell
$h = @{Authorization = "Bearer $($login.token)"}
$task = Invoke-RestMethod -Uri http://127.0.0.1:8000/tasks -Method Post -Headers $h -Body (@{objective='export my reminders'} | ConvertTo-Json) -ContentType 'application/json'
Invoke-RestMethod -Uri "http://127.0.0.1:8000/tasks/$($task.id)/transition" -Method Post -Headers $h -Body (@{to_status='IN_PROGRESS'} | ConvertTo-Json) -ContentType 'application/json'
$ask = Invoke-RestMethod -Uri "http://127.0.0.1:8000/tasks/$($task.id)/tools" -Method Post -Headers $h -Body (@{tool='export_calendar'} | ConvertTo-Json) -ContentType 'application/json'
Invoke-RestMethod -Uri http://127.0.0.1:8000/approvals -Headers $h
Invoke-RestMethod -Uri "http://127.0.0.1:8000/approvals/$($ask.approval_id)/decide" -Method Post -Headers $h -Body (@{approve=$true} | ConvertTo-Json) -ContentType 'application/json'
```

The export pauses the task until you decide: approving writes a real
`.ics` file into the `outbox` folder and completes the task, denying
fails it honestly. Every request, decision, and execution is stamped on
the task's audit trail; tool failures land in `GET /failures` with a
report instead of a false completion.

To skip the click for a fully trusted tool, name it in `.env` and
restart the server:

```powershell
# in .env
AUTO_APPROVE_TOOLS=export_calendar
```

The tool then executes at once. The approval row is still recorded
(note "auto-approved by AUTO_APPROVE_TOOLS policy") and the task's
audit trail keeps every event; anything not listed keeps pausing for
your decision, and an unknown name stops the server at startup so a
typo can never silently widen access. Only allowlist tools whose
effects you accept sight unseen — auto-approve means no human check.

## Operator backend (threads, outcomes, providers)

```powershell
$Headers = @{ Authorization = "Bearer $token" }

# Threaded chat: later turns remember earlier ones.
$thread = Invoke-RestMethod http://127.0.0.1:8000/threads -Method POST `
  -Headers $Headers -ContentType "application/json" -Body '{"title":"trip"}'
Invoke-RestMethod http://127.0.0.1:8000/chat -Method POST -Headers $Headers `
  -ContentType "application/json" `
  -Body (@{message="My favourite colour is blue"; thread_id=$thread.id} | ConvertTo-Json)

# Outcomes: a goal becomes an open parent with real child steps.
Invoke-RestMethod http://127.0.0.1:8000/outcomes/plan -Method POST -Headers $Headers `
  -ContentType "application/json" -Body '{"goal":"organise a picnic","place":"London"}'
# Revise it later: kept steps stay, dropped PENDING steps go BLOCKED (never deleted).
Invoke-RestMethod http://127.0.0.1:8000/outcomes/1/revise -Method POST -Headers $Headers `
  -ContentType "application/json" -Body '{"change":"invite grandparents too"}'
# Follow-ups are real reminders, so the worker delivers them.
Invoke-RestMethod http://127.0.0.1:8000/outcomes/1/followup -Method POST -Headers $Headers `
  -ContentType "application/json" `
  -Body '{"when":"2026-11-05T09:00:00+00:00","note":"check picnic plan"}'

# Providers: honest integration statuses (connected / available / missing).
Invoke-RestMethod http://127.0.0.1:8000/providers -Headers $Headers
Invoke-RestMethod http://127.0.0.1:8000/providers/weather/check -Method POST -Headers $Headers
```

Every model-calling agent inherits the shared constitution
(`constitution.py`, version pinned and tested). Weather is real and
keyless (Open-Meteo); calendar, email, video, and TTS report exactly
what they need instead of pretending to be connected.

## Demo bookings (the full idea, safely)

My Life → Bookings walks the complete booking journey — search a
deterministic demo catalog, pick an option, approve the real approval
gate, receive a DEMO-XXXX confirmation, cancel through a real
cancellation task. Everything runs on genuine Saath machinery (tasks,
approvals, audit); only the provider at the end is fictional, and
every screen, code, and receipt says so. Demo tools always ask: they
can never be added to `AUTO_APPROVE_TOOLS`.

The catalog covers everyday needs: cabs, appointments (dentist, salon,
doctor, spa), services (car wash, lawyer), and party hosting with
RSVP invites. Service and venue listings carry address, distance, and
hours shaped like map results — each labeled a sample, showing where
live Google Maps Places data would plug in. Party invites go to
fictional contacts (name + relation only, no real details), and sample
RSVPs appear only when explicitly requested, labeled as samples.

## Google Calendar (first real integration)

My Life → Google Calendar connects your actual Google account with a
Desktop-app OAuth flow: Connect opens Google in a new tab, you approve
the events-only scope, Google lands back on this machine's
`/calendar/callback`, and Saath stores a per-user refresh token.
Access tokens are minted per call and never stored. The consent asks
only to read/write events and see your email address.

What it does: "Show my events today" reads the real day; "Add to
Google Calendar" on a confirmed appointment or party booking sends a
`calendar_add_event` tool call through the normal approval gate, and
approving creates the genuine event — the task result carries Google's
real event ID and link as proof. Revoked sign-ins mark the link
broken with the reconnect remedy instead of failing silently.
Disconnect forgets the token; your Google events stay put.

Setup (one time): Google Cloud Console → new project → enable the
Calendar API → OAuth consent screen (External, yourself as test user)
→ Credentials → OAuth client ID → Desktop app. Put the two values in
`.env` as `GOOGLE_CALENDAR_CLIENT_ID` and
`GOOGLE_CALENDAR_CLIENT_SECRET`, restart the server. Without both,
the Providers screen reports calendar as missing with the exact need.

## Gmail (second real integration, send-only)

My Life → Gmail connects with the same Google Cloud OAuth client as
calendar, but a separate send-only grant: Connect opens Google, you
approve mail-send + email display, Saath stores a per-user refresh
token. Compose a message, send it to Approvals, and approving
delivers the genuine email — the task result carries Google's real
message ID as proof. There is deliberately no inbox reading: the
scope cannot read mail, no read tool exists, and the Providers Check
only verifies the grant without sending anything.

Setup: enable the Gmail API on the same Cloud project (no new keys).
Revoked grants mark the link broken with the reconnect remedy;
Disconnect forgets the token while sent mail stays sent.

## Google Maps (third real integration, live places + routes)

Bookings tabs carry live-data buttons next to the demo catalog: cabs
get "Get real route & time" (driving/walking/transit/cycling), while
appointments, services, and parties get "Find real places" —
name, address, rating, and open-now from Places API (New), and
distance/duration/steps from the Routes API. Live results wear a
LIVE badge and never mix with DEMO-labeled bookings.

Every call bills fractions of a cent, so three guards stack:
`GET /maps/places` and `GET /maps/route` refuse past the local
`GOOGLE_MAPS_DAILY_CAP` (default 200/day), the Cloud key must be
restricted to the Places + Routes APIs, and a $1 Cloud budget alert
is required. The Providers Check spends one tiny disclosed request.
Read-only `maps_search_places` / `maps_route` tools exist for future
chat routing; denied keys, dead zones, and quota exhaustion all
surface as plain errors, never fake listings.

Setup: Cloud Console → enable Places API (New) + Routes API →
API key restricted to those two → `GOOGLE_MAPS_API_KEY` in `.env` →
restart. Without the key, Maps reports missing with the exact need.

## AI video lessons (Local Studio works, Runway still needs a key)

The full pipeline is implemented, tested, and demonstrated live: Muse
plans the lesson (reused tutor planner), Muse Image draws per-scene
keyframes, a footage provider renders motion clips, and Saath assembles
the MP4 with SRT captions + transcript. Jobs advance one step per
worker tick through `PENDING → PLANNING → GENERATING_ASSETS →
GENERATING_VIDEO → ASSEMBLING → VERIFYING → COMPLETED`, with
`PENDING_APPROVAL` gating paid footage, `FAILED`/`CANCELLED` handled
honestly, quotas (2 active, 5/day), per-user ownership, and private
files under `media/`.

Three providers, never confused:

- `local-demo` — **Muse-powered illustrated video**: Muse planning +
  illustrations, scenes animated locally with FFmpeg (zoom/pan,
  titles, fades), narration from the computer's own voices, real
  playable MP4. No key needed. Rendering is free on your device;
  Muse calls still use API quota.
- `runway` — genuine AI-generated moving footage. Needs
  `RUNWAYML_API_SECRET` in `.env` (Meta's Model API has no video
  endpoint — verified October 2026: text, image, transcription,
  segmentation only). Runway jobs refuse at creation naming the
  missing key until you add it.
- `fake` — labeled test bytes for the automated suite
  (`live_footage: false`).

Shorts can be wide (landscape, 1280×720) or tall (portrait,
720×1280, shorts only); tutorials and scenarios are wide. The
planner retries once, shorter, if the model truncates a long plan;
follow-up questions do the same.

Endpoints: `POST /video/jobs` (`topic`, `format` short/tutorial/
scenario, `duration_s`, `context`, `image_data_url`, `provider`,
`orientation`), `GET /video/jobs`, `GET /video/jobs/{id}`, `POST /
video/jobs/{id}/confirm`, `POST /video/jobs/{id}/cancel`, `DELETE /
video/jobs/{id}`, `GET /video/jobs/{id}/file`, `GET /video/jobs/{id}/
captions`, `POST /video/jobs/{id}/ask`, `GET /video/jobs/{id}/
keyframes`. Learn → Videos is the player UI: pick local/runway/test
footage, choose wide or tall for shorts, watch honest progress with
the scene being made highlighted, confirm paid spends, play with
speed + captions, browse scenes, read the transcript, and ask
follow-up questions.

The worker starts with the server and scans for due reminders every

To hold notifications overnight, store a `quiet-hours` preference
(`user` layer, `preference` category, value like `22:00-07:00` in UTC):
ticks during the window report the reminders as held instead of
notifying. Mark one read with
`POST /notifications/{id}/read` (a still-due reminder nags again next
pass until you complete it).

## Safety limits

- Logins lock for 15 minutes after 5 wrong attempts (even for
  usernames that do not exist, so timing reveals nothing).
- Passwords: 8–256 characters; objectives and chat messages: 2000;
  memory values: 4000; smaller caps on keys, names, and notes.
- The server refuses to start with a Contributor-tier model ID or a
  non-standard model mode (training-on-your-data risk).
- Delegation chains cap at depth 3 and loops are rejected; approvals
  are single-use and expire; secrets live only in `.env`.
